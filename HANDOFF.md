## 1. Что уже реализовано

### Конвейер разбора и сверки

- **Разбор проектной документации.** Из текста извлекаются требования с
  привязкой к разделу, тому и странице. Состав комплекта (сколько листов
  чертежей, сколько текстовых, что не прочиталось) считается **всегда**, до
  обращения к модели и независимо от неё.
- **Разбор рабочей документации** тем же механизмом.
- **Сверка** лестницей из трёх ступеней: совпадение обозначения в тексте →
  смысловая сверка текста моделью → просмотр листов зрением. Дорогая ступень
  включается только там, где дешёвые не дали ответа.
- **Разделение извлечённого на три вида** (последнее по времени, Г.117):
  требование → в сверку; исходные данные расчёта → показываются, не сверяются;
  позиция ведомости → отдельное сравнение списков по обозначению изделия.
- **Сверка ведомостей** различает «есть в РД», «в РД другая марка того же ряда»
  (замена оборудования) и «не найдено».
- **Карта внимания** — очередь эскалации: что подтвердил только один источник.

### Хранение

- **Хранилище оригиналов** (`file_store.py`): содержимое по SHA-256, дедупликация
  по отпечатку, срок хранения, ручное удаление ничейного файла, выкладка в кэш
  по требованию.
- **Память разбора** (`facts_store.py`): разбор страниц считается один раз,
  ключ — отпечаток содержимого плюс версия разборщика. Раньше та же работа
  делалась четырежды за прогон.
- **Разрезание тяжёлых томов** по весу с сохранением исходной нумерации листов.
- **Хранилище результатов разбора** (`pd_store.py`) — передача между стадиями
  и накопление датасета.

### Работа с прогонами

- Загрузка отвечает мгновенно, разбор идёт в фоне.
- Прогресс честный: доля из факта, оценка остатка по скорости этого прогона,
  название текущей ступени. Пока измерить нечего — полоса не рисуется.
- **Остановка** любого длинного дела кнопкой (разбор, сверка, анализ, карта
  внимания). Флаг, а не убийство потока: прерывание в безопасной точке.
- **Продолжение после перезапуска сервера**: оборванные прогоны запускаются
  заново, остановленные инспектором — нет.

### Интерфейс

Три экрана: «Новый анализ», «Разобранная документация» (выжимка по каждому
тому + постранично по требованию + прогоны и извлечённые требования), «Карта
внимания». Документы берутся с сервера, а не из памяти браузера.

### Инфраструктура

Запуск одной командой (`scripts/start-all.sh`, `START-NADZOR.bat` для Windows
через WSL), автоматическая сборка набора корневых сертификатов из `certs/`,
поиск ключа провайдера в трёх местах, диагностика связи по шагам, CI на
GitHub Actions, сканеры безопасности.

## 2. Какие решения приняты и почему

| Решение | Причина |
|---|---|
| **Три отдельные базы** (прогоны / оригиналы / разбор) | Оригинал велик, читается редко и должен уметь исчезнуть по сроку; разбор мал, читается постоянно и переживает удаление файла. В одной базе либо таскаешь гигабайты при каждом обращении к разбору, либо не умеешь удалить оригинал отдельно. |
| **Ключ всех хранилищ — отпечаток содержимого** | Тот же том под другим именем уже разобран. Дедупликация не оптимизация, а следствие ключа. |
| **Версия разборщика в ключе памяти** | Меняется код извлечения — прежние записи перестают подходить сами, без ручной чистки и без риска отдать разбор по старым правилам. |
| **Разбор в фоне, а не в ответе на загрузку** | Том в сотни листов держал браузер 167 секунд, и инспектор не мог понять, работает программа или зависла. |
| **Документы с сервера, а не из localStorage** | Копия в браузере переживала пересборку базы, удаление в другой вкладке и чужой прогон: показывались тома, которых на сервере уже нет. Один корень у трёх разных жалоб. |
| **Остановка флагом, а не убийством потока** | Оборвать запрос к провайдеру на полуслове нельзя безопасно. Поэтому остановка наступает на ближайшей развилке, и интерфейс говорит именно это. |
| **Оборванные прогоны запускаются заново, а не «продолжаются»** | Промежуточного состояния разбора нигде нет — продолжать нечем. Заново теперь дёшево: разбор страниц берётся из памяти, платными остаются только вызовы модели. |
| **Схема базы дописывается, а не пересоздаётся** | Пересборка при любом расхождении стёрла введённый вручную ключ вместе с историей. Настройки — не история прогонов: их из кода не восстановить. |
| **Ключ провайдера — файлом в `secrets/`, а не полем интерфейса** | Введённый в интерфейсе ключ живёт в базе, а база производна: её пересобирают и чистят. Файл переживает и обновление, и пересборку. В git каталог не идёт. |
| **Разделение по форме записи, а не по теме** | Требование, исходные данные и позиция ведомости различаются наличием глагола/норматива и буквенно-цифровой марки. Правило не знает предметной области и потому переносится на любой раздел документации. |
| **Умолчание классификатора — «требование»** | Проверить лишнее стоит вызова модели, не проверить — стоит пропущенного нарушения. |
| **Подтверждение только по марке, не по бренду** | Название завода где-то в комплекте засчитывалось как присутствие конкретного изделия. Ложное подтверждение опаснее пропуска: пропуск инспектор увидит в списке «посмотреть», подтверждённое он больше не откроет. |
| **Ранжирование вместо отсева** | Порог, выведенный из одного комплекта, — не правило. Сколько взять из порядка, решает бюджет потребителя. |

## 4. Что не работает

- **Связь с провайдером модели на машине пользователя.** Авторизация GigaChat
  идёт на порт 9443 — там таймаут, при том что 443 отвечает. Гипотеза:
  исходящий 9443 закрыт фаерволом или антивирусом. **На машине пользователя не
  подтверждена** — вывод `scripts/check_gigachat.py` оттуда не получен.
- **Линтер и сканеры безопасности красные** — см. § 6.
- **Подбор листов-кандидатов схлопывается.** Почти всем требованиям
  предлагаются одни и те же 3 листа, и зрение сотни раз смотрит на одно и то
  же. Это главная причина, по которой сверка идёт полтора часа.
- **Качество извлечения.** Модель выписывает как требование то, что им не
  является по смыслу. Разделение по форме (Г.117) — фильтр грубый и честно
  назван таким; смысловых ложных срабатываний он не ловит.

## 8. Рекомендуемый следующий шаг

**Подбор листов-кандидатов.** Причина: это единственная незавершённая задача,
которая одновременно снижает стоимость прогона (полтора часа → минуты) и
повышает качество отчёта (сейчас инспектору предлагают открыть одни и те же три
листа под сотню разных требований, что обесценивает подсказку).

Направление, не решение: сейчас лист выбирается по номеру помещения, а когда
номера нет — по подсказке названия и по отметке этажа. На комплекте, где
подписи чертежей переведены в кривые, все три способа дают почти пустой
результат, и остаётся общий резерв. Смотреть надо на то, чтобы **ранжировать**
листы (правило 3 из порядка правок), а не отбирать по порогу, и чтобы бюджет
просмотра тратился на **разные** листы, а не на повторные.

Обязательное условие: любое правило подбора формулируется без единого слова о
разобранном комплекте, иначе `make check-generic` его не пропустит — и это
правильно.

## 9. Важные детали из переписки, которых нет в коде

Это то, что определяло решения, но в комментариях не поместилось.

- **«Много мусора в тексте, разве не видно»** — постоянное требование
  пользователя: отчёт должен быть коротким и читаемым, а не полным. Полнота без
  читаемости не считается результатом. Отсюда группировка отчёта по разделам и
  порядок «сначала то, где названы листы».
- **«Опять именно под примеры подтачиваешь»** — правило 8 нарушалось десять раз
  подряд, каждый раз незаметно для автора, и каждый раз это находил
  пользователь. Поэтому появились машинные проверки. Если `make check-generic`
  падает — это не формальность, а тот самый случай.
- **«Мне кажется, ты меня где-то обманываешь»** — сказано, когда в браузере
  открывалась старая версия. Отсюда правило: у любого состояния должен быть
  видимый признак. Карточка «Версия» в интерфейсе, печать версии при запуске,
  `scripts/runs.py` — всё родилось из этой претензии.
- **Пользователь тестирует на реальном комплекте**, а не на демо-данных. Любая
  правка проверяется на нём, поэтому «на моём примере работает» ничего не
  значит, пока правку нельзя объяснить, не называя этот комплект.
- **Формулировки в отчёте — часть продукта.** «Требует проверки» ≠ «нарушение»,
  «не найдено» ≠ «отсутствует». Оговорки убирать нельзя: без них отчёт из
  508 строк читается как 508 обвинений.
- **Пользователь просил «вшить ключи в программу».** Отказано осознанно и
  объяснено: ключ в репозитории становится общедоступным. Компромисс — файл в
  `secrets/`, который даёт тот же результат («настроено сразу») без утечки.
  Если просьба повторится — ответ прежний.
- **Ветка одна**: `claude/new-session-d44es2`. В неё же ранее писал другой
  агент (GigaCode, см. `GIGACODE.md`).
- **Стоимость важна.** Каждый вызов модели платный, и пользователь это
  отслеживает. Решения вида «прогнать зрение по всему тому» отвергались по
  этой причине, а не по технической.
