# НАДЗОР.ИИ — облегчённый бэкенд (домашний прототип)

Отдельный, более простой бэкенд под конкретную механику сравнения
документации — **не замена** `packages/api` (полный CRM-бэкенд с RBAC и
аудит-цепочкой уже существует там и живёт своей жизнью). Здесь: один
пользователь, SQLite, без Docker — запускается одной командой на домашнем ПК.

## Запуск

```bash
cd packages/backend
./run.sh   # первый раз создаст .venv и поставит зависимости, дальше просто поднимет сервер
```

Сервер на `http://127.0.0.1:8010`, автодокументация — `/docs`.

Локальная LLM (Ollama) по умолчанию — **данные не покидают компьютер**;
внешний API (OpenAI/Anthropic/Google) подключается через `PUT /settings`,
если нужна скорость важнее приватности.

## Механика (зачем эти файлы)

**Проблема, которую всё это решает**: тупое сравнение всего текста со всем
текстом даёт кучу мусора — инспектор получает страницы «расхождений» без
смысловой нагрузки, и неясно, что вообще кормить модели для сравнения.

Решение — три шага вместо одного:

1. **`classification.py`** — определяет раздел документа (АР/КР/ОВ/ВК и т.п.)
   по шифру, **до** любого сравнения. Шифр всегда заканчивается кодом
   раздела (так требует ГОСТ Р 21.1101) — читаем имя файла → титульный лист
   → штамп текстом → штамп через vision-модель, если там нет текстового
   слоя (частый случай на исполнительной документации — штамп там нередко
   растровая картинка, не текст; проверено на реальных образцах из этой
   сессии).
2. **`matching.py`** — сопоставляет листы ПД и РД/ИД **внутри одного
   раздела**, а не по случайному пересечению слов. Если раздел не удалось
   определить — работает как раньше (без гейтинга), листы без пары не
   выкидываются, а уходят в позиционный резерв с явной пометкой низкой
   уверенности.
3. **`vision.py` / `diffing.py` / `llm.py`** — само сравнение уже сопоставленной
   пары, с контекстом раздела в промпте и строгим JSON-выводом
   (`response_format: json_object`) — так модель не уходит в посторонние
   рассуждения вместо ответа по задаче.

## Известные упрощения (сознательные, не забытые)

- **Реестр помещений** (парсинг «Экспликации помещений» построчно) из
  браузерного инструмента (`nadzor-browser/app.js`) сюда не портирован —
  `text_facts` уже достаточно для гейтинга по разделу и текстового diff;
  `room_facts` в схеме предусмотрен и пуст, добавляется отдельным шагом без
  переделки остального.
- **Штамп читается только на первом листе документа**, не на каждом — один
  vision-вызов на файл, а не на страницу, чтобы не разорять бюджет на
  больших комплектах. Для «тома» из нескольких разных чертежей внутри
  одного PDF это упрощение может ошибаться — стоит проверить на реальных
  комплектах пользователя.
- **Список кодов разделов** (`DISCIPLINE_CODES` в `classification.py`) —
  буквенные коды по ГОСТ Р 21.1101. Числовые шифры по Постановлению №87
  (например, «ИОС5.4.2» вместо буквы) не разбираются намеренно — это другая
  система нумерации, риск ложных совпадений выше пользы.
- Текстовые факты (`text_facts`) не персистятся в БД — извлекаются заново из
  файла на каждый запуск анализа. Файл на диске остаётся источником истины;
  это сознательный компромисс простоты для одиночного домашнего инструмента.

## Тесты

```bash
cd packages/backend
../../.venv/bin/python tests/test_classification.py
../../.venv/bin/python tests/test_matching.py
../../.venv/bin/python tests/test_diffing.py
../../.venv/bin/python tests/test_llm.py
../../.venv/bin/python tests/test_vision.py
../../.venv/bin/python tests/test_integration_real_docs.py   # на реальных образцах документов
../../.venv/bin/python tests/test_api_integration.py          # сквозной прогон через настоящий HTTP API
```

Все LLM-вызовы в тестах замоканы (сеть не нужна) — кроме
`test_integration_real_docs.py`/`test_vision.py`, где vision-ответ подставлен
тем, что реально написано на штампе реального образца (проверено визуально
в этой сессии), чтобы тест проверял настоящую логику, а не выдуманную.
