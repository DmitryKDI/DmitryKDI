# НАДЗОР.ИИ

Модуль предиктивного строительного надзора для цифровой экосистемы стройкомплекса
Москвы. Задача города № 10, Комитет государственного строительного надзора
города Москвы.

[![Проверки](https://github.com/DmitryKDI/DmitryKDI/actions/workflows/nadzor-ui.yml/badge.svg)](../../actions/workflows/nadzor-ui.yml)

## Что делает

ИИ-сервис сверяет проектную (ПД), рабочую (РД) и исполнительную (ИД)
документацию объекта по матрице параметров ТЗ и готовит инспектору протокол
до выезда на объект:

1. **Приём комплекта** — файлы PDF, DOCX или XML с реестром (шифр, редакция,
   статус утверждения, предшественник). Для каждого шифра выбирается актуальная
   редакция; сканы распознаются локально.
2. **Сверка по матрице** — по каждому параметру модель читает страницы всех трёх
   стадий и возвращает значения с цитатой, листом и координатами. Расхождение
   становится кандидатом, совпадение с доказательствами с обеих сторон —
   предварительным отрицательным результатом. Отдельно идёт графическая сверка
   листов.
3. **Решение инспектора** — подтвердить или отклонить с кодом причины;
   «Завершить» фиксирует протокол, после чего его можно выгрузить в JSON, XML,
   DOCX или PDF и передать пакетом во внешнюю систему.

Результат — **гипотезы для проверки, а не заключение о нарушениях**.
Параметр, по которому не хватило данных или проверка не выполнилась, так и
помечается и не выдаётся за «нарушений нет». Подтверждает нарушение только
инспектор.

## Официальный запуск: закрытый контур без Интернета

Все модели работают локально, внешних API нет. Обращение к адресу вне контура
запрещено в коде (`app/llm.py`): разрешены только loopback, частные сети и
имена сервисов docker compose. Сеть `contour`, в которой работает модель,
объявлена `internal` — выхода наружу у неё нет вообще.

Стенд: Linux, Docker с compose, NVIDIA-драйвер и NVIDIA Container Toolkit,
1× GPU (проверено по требованиям на H100 80 GB). Драйвер в комплект не входит,
CUDA runtime — внутри образа сервера модели.

**Один раз, на машине с Интернетом** — собрать офлайн-комплект:

```bash
scripts/offline/prepare_bundle.sh
```

Скрипт скачивает образ сервера модели по дайджесту, веса модели в `models/`
(ревизия фиксируется коммитом репозитория модели), собирает образы backend и
frontend и сохраняет всё в `bundle/` вместе с `bundle/MANIFEST.txt` (ревизия
весов, ID образов, SHA-256 файлов). `models/` и `bundle/` в git не идут.

**На стенде, без Интернета** — одна команда:

```bash
scripts/offline/load_bundle.sh
```

Она загружает образы, сверяет их ID с манифестом и выполняет
`docker compose up -d --no-build`. Если образы уже загружены — достаточно
`docker compose up -d`.

| Адрес | Что |
|---|---|
| http://localhost:5173 | интерфейс инспектора |
| http://localhost:8010/docs | OpenAPI 3.0 (Swagger), схема — `/openapi.json` |
| http://localhost:8010/health | healthcheck движка |

Первый старт модели — несколько минут (загрузка весов в GPU); `docker compose ps`
показывает `healthy`, когда всё готово. Backend ждёт готовности модели.

## Программный интерфейс: асинхронная pull-модель (ТЗ 1.3–1.4, 9)

REST/JSON, схема OpenAPI 3.0.3 (`/openapi.json`, `/docs`; выгружена в
[docs/openapi.json](docs/openapi.json), проходит `openapi-spec-validator`).
Внешний контракт — `/api/v1`:

```text
POST /api/v1/documents/upload                 files[] + registry (JSON/CSV) → {process_id, status: PENDING,
                                              upload_status, scenario, accepted[], rejected[]}
                                              process_id в форме — дозагрузка в существующий процесс
GET  /api/v1/processes/{process_id}/status    мониторинг: статус, этап, прогресс
GET  /api/v1/processes/{process_id}           протокол: статус загрузки, сценарий, пять таблиц, версии
POST /api/v1/processes/{process_id}/decisions решение инспектора (при отклонении — reason_code)
POST /api/v1/processes/{process_id}/finalize  «Завершить»: только когда у всех кандидатов есть решение
POST /api/v1/processes/{process_id}/unfinalize отмена — администратор/супервизор, с причиной, в журнал
GET  /api/v1/processes/{process_id}/export?format=json|xml|docx|pdf
POST /api/v1/inspection/{process_id}          пакет для ИАИС «РиН»: только FINALIZED, только подтверждённое
```

| Что | Значения |
|---|---|
| Статус процесса | `PENDING` → `PARSING` → `READY` → `VERIFYING` → `COMPLETED` → `FINALIZED` (+ `ERROR`, `CANCELLED`) |
| Статус загрузки | `PD/RD/ID_UPLOADED`, `_PARTIAL`, `_MISSING` |
| Сценарий | `FULL`, `PD_RD_ONLY`, `PD_ID_ONLY`, `RD_ID_ONLY`, `SINGLE_ONLY`, `PARTIALLY_LOADED` |
| Полнота | `COMPLETE`, `MISSING_EVIDENCE`, `NOT_APPLICABLE`, `NOT_COMPARABLE`, `CLARIFICATION_REQUIRED` |
| Находка | `CANDIDATE`, `NEGATIVE_VERIFIED`, `CONFIRMED_VIOLATION` (только инспектор), `SUSPICION` |

Реестр файлов (перечень ИД): `file_id`, `file_name`, `object_id`, `doc_stage`, `document_code`,
`revision`, `approval_status`, `approval_date`, `predecessor_id`, необязательно `sha256`,
`sheet_page_range`, `signature_status`. Без реестра пакет принимается, но каждый параметр
получает `CLARIFICATION_REQUIRED`. Лимиты: 50 МБ на файл, 200 МБ на пакет. Форматы — PDF,
DOCX, XML (по содержимому, а не расширению): DOCX и XML при приёме приводятся к PDF, исходный
формат и его SHA-256 сохраняются в метаданных; XML с DTD не принимается (защита от XXE).
Сбой проверки повторяется до двух раз.

Распознавание сканов: у каждой распознанной страницы качество `OK`, `LOW_QUALITY` (символы
есть, слов нет) или `ABSTAIN` (не распознано); в протоколе — покрываемость по документам,
у доказательства — пометка, если цитата взята со страницы с низким качеством.

Дозагрузка (ТЗ 9.2) — инкрементальная. Если состав актуальных редакций не изменился
(дубликат, заменённая или неутверждённая редакция), прежний протокол переиспользуется без
вызова модели. Если изменился — пересчитываются только параметры, для которых в новых
документах есть данные (сработал шаблон разбора или встретилось слово наименования
параметра), а также параметры с неполной прежней проверкой или с доказательством из
редакции, переставшей быть актуальной. Остальные результаты переносятся вместе с решениями
инспектора; решение, принятое по прежнему результату пересчитанного параметра, к новому не
применяется. Перечень пересчитанных — в `result.incremental`. Прежняя версия протокола
сохраняется в истории.

Протокол содержит раздельные таблицы: комплектность, кандидаты, подтверждённые,
проверенные отрицательные, гипотезы свободного поиска. Карточка кандидата: `finding_id`,
параметр, `expected/actual/delta`, по каждому источнику `file_id`, SHA-256, стадия, шифр,
редакция, статус утверждения, страница, bbox в [0;1], `approved_change_ref`, решение и
причина инспектора. Версии в каждом протоколе: `matrix_version`, `model_version`,
`dataset_version`, `input_manifest_hash`. При дозагрузке прежняя версия протокола
сохраняется.

Пример ответа — [docs/example-output.json](docs/example-output.json) (синтетические
документы, ответ модели задан сценарием; файл собирает настоящий код:
`scripts/make_example_output.py`). Параметр, по которому проверка не выполнилась, не
выдаётся за «нарушений нет»: `technical_status: "not_run"` и причина.

## Пользователи, матрица и свободный поиск

**Вход и роли (ТЗ 12).** Всё, кроме `/health` и входа, требует сессии: `POST /api/v1/auth/login`
(логин и пароль → cookie и bearer-токен), `POST /api/v1/auth/logout`, `GET /api/v1/auth/me`.
Роли: `inspector` (решения, финализация), `supervisor` (то же + отмена финализации),
`admin` (пользователи, матрица, нормы, правила, настройки), `ml_engineer` (чтение, журнал
аудита), `service` (внешняя система: загрузка и забор результата). Пароли — scrypt с солью.
Первый администратор — из `NADZOR_ADMIN_LOGIN` / `NADZOR_ADMIN_PASSWORD`, иначе пароль
генерируется и записывается в `initial-admin-password.txt` рядом с базой (права 0600).
Каждое изменяющее действие пишется в журнал аудита с пользователем, IP и агентом:
`GET /api/v1/admin/audit`.

**Матрица в базе (ТЗ 8.1, модуль 8).** Официальные 132 параметра при первом запуске
переносятся в таблицу `params`; администратор меняет пороги, ссылки на СП/ГОСТ/ФЗ, тип
значения, шаблон разбора и активность без перекодирования:

```text
GET   /api/v1/admin/params                  параметры, включая неактивные
PATCH /api/v1/admin/params/{code}           правка параметра; каждая правка — новая ревизия матрицы
GET|POST /api/v1/admin/normative, PUT /api/v1/admin/normative/{id}   нормативная база
GET|POST /api/v1/admin/rules,     PUT /api/v1/admin/rules/{id}       логические правила
```

Проверяются все активные параметры (ТЗ 9.2). Выход значения за `min_value`/`max_value`
определяет код (`threshold_status`), а не модель. Версия матрицы в протоколе — `1.1` или
`1.1-rN` после N правок.

**Свободный поиск гипотез (ТЗ 9.5).** После проверки по матрице — четыре подхода:
логические правила «если A, то B» (`M-001 > 10` → `present(M-002)`), семантический
диссонанс названий помещений в ПД и РД/ИД, нормативный анализ по действующим на дату
нормам, аномалия значения относительно других объектов (не меньше 5 объектов, правило
трёх сигм). Гипотеза — `SUSPICION` в структуре ТЗ, хранится в таблице `suspicions`,
не входит в число нарушений. `GET /official/runs/{id}/suspicions`;
`POST /official/runs/{id}/suspicions/{suspicion_id}` с `action`: `promote` (в кандидаты —
только с листом и координатами в ПД и РД/ИД), `dismiss`, затем `confirm` / `reject`.

## Обратная связь и управляемое дообучение (ТЗ 9.4, модули 4 и 10)

Решение инспектора сразу размечается: `CONFIRMED_VIOLATION` — положительный
GOLD-кандидат, `NEGATIVE_VERIFIED` — отрицательный пример и запись в `rejection_log`
(причина, машинный вердикт, рекомендация), `CLARIFICATION_REQUIRED` — в GOLD не идёт,
спорный случай в `dispute_log`. К каждому решению — системный комментарий в
формулировках ТЗ (`system_comment`). Весов сервис не обучает: обучение выполняется
на стенде с GPU, сюда регистрируются его результаты.

```text
GET  /api/v1/ml/dataset/items?status=DRAFT      черновик набора
POST /api/v1/ml/dataset/items/{id}/curate       решение куратора (ML-инженер)
POST /api/v1/ml/dataset/versions                выпуск dataset_version: только одобренное
                                                из финализированных протоколов; разбиение по
                                                объектам, SHA-256 каждого набора
GET  /api/v1/ml/dataset/versions/{v}/evaluate   Precision / Recall / F1 / FPR по разделам
GET  /api/v1/ml/rejections, /api/v1/ml/disputes журналы отклонений и спорных случаев
POST /api/v1/ml/models                          результат обучения → приёмка по ТЗ 14.3
POST /api/v1/ml/models/{id}/approve|reject      подпись публикации (администратор)
POST /api/v1/ml/models/{id}/rollback            откат к предыдущей опубликованной
GET  /api/v1/ml/report?days=7, /api/v1/ml/reports   отчёт по отклонениям с рекомендациями
```

Приёмка: Precision ≥ 0,90, Recall ≥ 0,80, F1 ≥ 0,85, FPR ≤ 0,10, и относительно
действующей модели Recall ни одной категории не падает, а FPR не растёт более чем на
2 п.п. Объект получает набор (train/validation/test) один раз и навсегда. Отчёт для
ML-инженеров формируется автоматически раз в неделю. `dataset_version` в протоколе —
у опубликованной модели.

## Интеграция с внешней системой

Внешняя система работает с сервисом через `/api/v1` (см. выше): загружает
комплект, опрашивает статус, забирает протокол. Обратная передача результатов —
`POST /api/v1/inspection/{process_id}` — включается одной переменной окружения:

```bash
# .env рядом с docker-compose.yml
NADZOR_RIN_URL=http://rin-gateway:8080/inbox   # адрес приёма; пусто — передача выключена
NADZOR_RIN_TOKEN=...                           # необязательно: Authorization: Bearer
NADZOR_RIN_CLIENT_CERT=/certs/client.pem       # клиентский сертификат (ТЗ 9.6)
NADZOR_RIN_CLIENT_KEY=/certs/client.key        # его закрытый ключ
NADZOR_RIN_CA=/certs/rin-ca.pem                # корневой сертификат приёмника
NADZOR_ALLOWED_HOSTS=rin.internal.local        # если адрес — внутреннее имя с точкой
```

Пакет (JSON): `process_id`, версии протокола, реестр входных файлов с SHA-256 и
только подтверждённые инспектором нарушения. Отправляется только из
финализированного протокола, с заголовком `Idempotency-Key: nadzor-{process_id}-v{версия}`
— повтор после сбоя приёмник опознаёт как повтор. Результат — в `sync_status`
процесса и в журнале событий протокола:

| `sync_status` | Что значит |
|---|---|
| `LOCAL_ONLY` | передача не включена, пакет только сформирован |
| `SENT` | приёмник ответил 2xx |
| `PENDING_SYNC` | приёмник недоступен (5xx, таймаут, обрыв): повтор через 1, 5 и 15 минут, каждая попытка — в журнале |
| `SEND_FAILED` | приёмник отказал (4xx) или повторы исчерпаны; причина в `sync_detail` |
| `SEND_REFUSED` | адрес вне контура — отправка не выполнялась |

Адрес проходит ту же проверку контура, что и модель: имя сервиса, частная сеть
или имя из `NADZOR_ALLOWED_HOSTS`. Выйти наружу опечаткой нельзя.

Сбой передачи не меняет финализированный протокол и решения инспектора. Расписание
повторов хранится в процессе и переживает перезапуск сервиса. TLS с ГОСТ-алгоритмами
(УКЭП) обеспечивает СКЗИ заказчика — шлюз перед приёмником; сервис предъявляет
клиентский сертификат стандартным TLS.

Документы, пришедшие в финализированный процесс, сохраняются, но проверку не
запускают: в ответе и в протоколе — уведомление (`pending_documents`), инспектор
создаёт новую проверку сам.

## Эксплуатация: логи, метрики, целостность, копии, антивирус (ТЗ 12–13)

| Требование | Как закрыто |
|---|---|
| Логи JSON (ТЗ 13, п.1–3) | `timestamp, level, service, message, request_id, user_id` в каждой строке; `X-Request-ID` принимается от внешней системы или назначается и возвращается; stdout для сборщика контура (ELK) и файлы в `/app/state/logs` с ротацией: общий — 90 дней, события безопасности — 365; DEBUG только вне `NADZOR_ENV=production` |
| Метрики (ТЗ 13, п.4–5) | `GET /metrics` (роль `service` или ML-инженер) в формате Prometheus: запросы и время ответа, 5xx, CPU и память, место на диске, активные сессии, очередь проверок, ожидающие передачи, результат проверки целостности. `docker compose --profile monitoring up -d` — Prometheus и Grafana, конфигурация в `deploy/monitoring/` |
| Алерты (ТЗ 13, п.7) | `deploy/monitoring/alerts.yml`: CPU > 80 %, среднее время ответа > 500 мс, 5xx, диск, целостность, непереданные протоколы; доставка по почте и в Telegram — Alertmanager контура |
| Целостность (ТЗ 13, п.8) | ежедневная сверка SHA-256 каждого оригинала и файла кэша; расхождение — событие безопасности в логе и метрика. `GET/POST /api/v1/admin/integrity` |
| Резервные копии (ТЗ 12, п.8; RPO ≤ 15 мин) | база процессов и решений — каждые 15 минут (хранятся сутки), все базы — ежедневно (30 дней); штатный online backup SQLite, отдельный том `nadzor-backups`. `GET/POST /api/v1/admin/backups` |
| Антивирус (ТЗ 12, п.11) | каждый файл до разбора и сохранения проверяется антивирусом контура по протоколу clamd (`NADZOR_CLAMD_HOST`; `docker compose --profile antivirus` поднимает ClamAV). Заражённый — отклоняется, антивирус недоступен — файл не принимается |
| TLS 1.3 (ТЗ 12, п.3) | положите `server.crt` и `server.key` в `./certs` — интерфейс откроется по `https://…:5443` только с TLS 1.3 |

## Проверка запуска без видеокарты

Модель на GPU проверяется только на стенде. Всё остальное — приём файлов,
протокол, решения, финализация, выгрузки, интерфейс — проверяется без GPU с
**дублёром модели** (`scripts/smoke/fake_model.py`): тот же протокол, что у vLLM,
ответы строятся механически из текста документов. Качество модели так не
проверяется, механика — полностью.

```bash
make smoke          # дублёр + движок на временных базах + 27 проверок сквозного сценария API

# весь состав в Docker, модель заменена дублёром:
docker compose -f docker-compose.yml -f docker-compose.smoke.yml up -d --build --wait
.venv/bin/python scripts/smoke/e2e_api.py --base-url http://127.0.0.1:8010
python scripts/smoke/ui_flow.py --url http://127.0.0.1:5173   # сценарий инспектора в браузере (Playwright)
docker compose -f docker-compose.yml -f docker-compose.smoke.yml down -v
```

Сквозной сценарий: загрузка ПД (PDF), РД (PDF), ИД (DOCX) с реестром → `process_id` →
статус `READY` → кандидаты с доказательствами (цитата, лист, bbox, SHA-256, шифр,
редакция) → решения инспектора → `FINALIZED` → запрет дозагрузки → выгрузка
JSON/XML/DOCX/PDF → пакет для ИАИС «РиН». Сценарий инспектора в браузере: заполнение
карточек, загрузка файлов через интерфейс, запуск, отклонение кандидата с кодом
причины, финализация, отсутствие ошибок на странице.

## Технологии ТЗ и применённые аналоги

Организаторы разрешили совместимые аналоги: обязательны не названия продуктов, а
проверяемое поведение.

| В ТЗ | В решении | Почему поведение сохраняется |
|---|---|---|
| Серверная часть на Node.js | Python 3.12, FastAPI | ML-модули ТЗ и так на Python; один язык — один процесс разбора и проверки |
| RabbitMQ | фоновые задачи FastAPI + статусы в БД | pull-модель с `process_id`, статусами, остановкой и повтором при сбое |
| Redis для кэша разбора | SQLite-хранилище разбора по SHA-256 файла | повторная загрузка того же файла не разбирается заново |
| PostgreSQL | SQLite в именованном томе | один стенд, одна команда запуска, данные переживают перезапуск |
| Sentence-BERT | локальная VLM сама сопоставляет текст | семантическое сопоставление без внешних сервисов |
| Prometheus/ELK | статусы, этапы и журнал событий протокола в БД | ход прогона, сбои, финализация и её отмена видны через API |

## Модели

| Назначение | Модель | Версия | Лицензия |
|---|---|---|---|
| Текст и изображения листов (VLM) | Qwen2.5-VL-7B-Instruct | ревизия весов — в `bundle/MANIFEST.txt` | Apache-2.0 |
| Сервер модели | vLLM (`vllm/vllm-openai`) | v0.28.0, образ закреплён дайджестом | Apache-2.0 |
| Распознавание сканов | Tesseract OCR, словари rus+eng | из Debian bookworm | Apache-2.0 |

Лицензии указаны по состоянию на подготовку комплекта; **перед сдачей сверить
с карточкой модели** на момент скачивания весов (из среды разработки карточка
была недоступна). Модель меняется переменными `NADZOR_MODEL_REPO`/`NADZOR_MODEL_DIR`
(скачивание) и `NADZOR_LOCAL_LLM_MODEL` (имя на сервере) без правки кода; при
смене нужно проверить, что её лицензия допускает коммерческое и государственное
использование — иначе она годится только для незачётного эксперимента.

Температура 0 и фиксированный seed сервера: повторный прогон на тех же
документах воспроизводим. Ответ, обрезанный по длине, считается сбоем проверки,
а не пустым результатом.

## Разработка

Нужны Python 3.11+ и Node.js 22. Модель — любой Chat Completions-совместимый сервер внутри
контура (`NADZOR_LOCAL_LLM_URL`, `NADZOR_LOCAL_LLM_MODEL`, см. `.env.example`).

```bash
make install              # виртуальное окружение и зависимости
./scripts/start-all.sh    # движок на 8010 и интерфейс на 5173 одной командой
```

Без сервера модели проверка не выдаёт пустой протокол за результат: параметры
получают `technical_status: "not_run"` с причиной. Без Tesseract сканы помечаются «движок распознавания
не установлен», а не «страница пуста».

## Безопасность

Основная угроза — **инъекция инструкций через проверяемый документ**: документы
предоставляет поднадзорное лицо, заинтересованное в сокрытии нарушений. Любой
текст документа, попадающий в промпт, помечен как недоверенный ввод. Подробно —
[docs/threat-model.md](docs/threat-model.md).

Документы и их фрагменты не покидают контур: внешних сервисов нет, сетевой
запрет стоит перед каждым вызовом модели. Ключей и секретов у решения нет.
Реквизиты проверяемых объектов в репозиторий не идут.

## Правовая модель

Система формирует **гипотезы**, а не заключения. Ни одно юридически значимое
действие не совершается автоматически. Оговорки о статусе выводов в отчётах —
часть продукта, а не вежливость: без них отчёт читается как обвинение.

## Ограничения

- Без запущенной локальной модели параметры получают `not_run` с причиной, а не
  «нарушений нет».
- Качество модели на реальных комплектах проверяется на стенде с GPU; в среде
  разработки механика проверена дублёром модели, а не весами.
- Из DOCX переносится текст абзацев и таблиц, без вёрстки и графики; из XML — текст
  элементов с путём к ним.
- Передача в ИАИС «РиН» по умолчанию выключена (адреса внешней системы на стенде нет):
  пакет формируется, `sync_status: LOCAL_ONLY`. Включается адресом приёма — см.
  «Интеграция с внешней системой». Формат приёма согласуется с владельцем системы;
  УКЭП — за пределами стенда.
- Сверка комплекта в сотни листов — десятки и сотни обращений к модели и
  десятки минут работы. Прогресс виден, прогон останавливается кнопкой.
- Шаблон протокола из Приложения № 2 к ТЗ не был предоставлен: протокол собран
  по тексту ТЗ (пять таблиц, карточки доказательств, версии).
