# НАДЗОР.ИИ

Модуль предиктивного строительного надзора для цифровой экосистемы стройкомплекса
Москвы. Задача города № 10, Комитет государственного строительного надзора
города Москвы.

## Что делает

Инспектор загружает комплекты документации и получает ответ на один вопрос:
**на что смотреть в первую очередь и почему**.

Работа идёт в три шага, каждый — отдельной кнопкой:

1. **Разбор проектной документации** — из текста извлекаются требования с
   привязкой к разделу, тому и странице. Состав комплекта (сколько листов
   чертежей, сколько текстовых, что не прочиталось) считается всегда, даже без
   связи с языковой моделью.
2. **Разбор рабочей документации** — тот же механизм, другая сторона комплекта.
3. **Сверка** — по списку требований проектной документации: что подтверждается
   текстом или чертежами рабочей, а что нужно посмотреть глазами. Совпадение
   обозначения само по себе не подтверждает требование. Текстовое подтверждение
   требует цитаты из указанного источника и оценки выполнения всего условия.

Результат — **гипотезы для проверки, а не заключение о нарушениях**. «Требует
проверки» означает «подтверждения не нашлось в доступных данных»: в рабочей
документации мало связного текста по природе, подписи чертежей переведены в
кривые. Решение принимает инспектор.

## Официальный запуск: закрытый контур без Интернета

Все модели работают локально, внешних API нет. Обращение к адресу вне контура
запрещено в коде (`app/llm.py`): разрешены только loopback, частные сети и
имена сервисов docker compose. Сеть `contour`, в которой работает модель,
объявлена `internal` — выхода наружу у неё нет вообще.

Стенд: Linux, Docker с compose, NVIDIA-драйвер и NVIDIA Container Toolkit,
1× GPU (проверено по требованиям на H100 80 GB). Драйвер в комплект не входит,
CUDA runtime — внутри образа сервера модели.

**Один раз, на машине с Интернетом** — собрать офлайн-комплект:

```bash
scripts/offline/prepare_bundle.sh
```

Скрипт скачивает образ сервера модели по дайджесту, веса модели в `models/`
(ревизия фиксируется коммитом репозитория модели), собирает образы backend и
frontend и сохраняет всё в `bundle/` вместе с `bundle/MANIFEST.txt` (ревизия
весов, ID образов, SHA-256 файлов). `models/` и `bundle/` в git не идут.

**На стенде, без Интернета** — одна команда:

```bash
scripts/offline/load_bundle.sh
```

Она загружает образы, сверяет их ID с манифестом и выполняет
`docker compose up -d --no-build`. Если образы уже загружены — достаточно
`docker compose up -d`.

| Адрес | Что |
|---|---|
| http://localhost:5173 | интерфейс инспектора |
| http://localhost:8010/docs | OpenAPI 3.0 (Swagger), схема — `/openapi.json` |
| http://localhost:8010/health | healthcheck движка |

Первый старт модели — несколько минут (загрузка весов в GPU); `docker compose ps`
показывает `healthy`, когда всё готово. Backend ждёт готовности модели.

## Программный интерфейс: асинхронная pull-модель (ТЗ 1.3–1.4, 9)

REST/JSON, OpenAPI 3.0 (`/docs`, `/openapi.json`). Внешний контракт — `/api/v1`:

```text
POST /api/v1/documents/upload                 files[] + registry (JSON/CSV) → {process_id, status: PENDING,
                                              upload_status, scenario, accepted[], rejected[]}
                                              process_id в форме — дозагрузка в существующий процесс
GET  /api/v1/processes/{process_id}/status    мониторинг: статус, этап, прогресс
GET  /api/v1/processes/{process_id}           протокол: статус загрузки, сценарий, пять таблиц, версии
POST /api/v1/processes/{process_id}/decisions решение инспектора (при отклонении — reason_code)
POST /api/v1/processes/{process_id}/finalize  «Завершить»: только когда у всех кандидатов есть решение
POST /api/v1/processes/{process_id}/unfinalize отмена — администратор/супервизор, с причиной, в журнал
GET  /api/v1/processes/{process_id}/export?format=json|xml|docx|pdf
POST /api/v1/inspection/{process_id}          пакет для ИАИС «РиН»: только FINALIZED, только подтверждённое
```

| Что | Значения |
|---|---|
| Статус процесса | `PENDING` → `PARSING` → `READY` → `VERIFYING` → `COMPLETED` → `FINALIZED` (+ `ERROR`, `CANCELLED`) |
| Статус загрузки | `PD/RD/ID_UPLOADED`, `_PARTIAL`, `_MISSING` |
| Сценарий | `FULL`, `PD_RD_ONLY`, `PD_ID_ONLY`, `RD_ID_ONLY`, `SINGLE_ONLY`, `PARTIALLY_LOADED` |
| Полнота | `COMPLETE`, `MISSING_EVIDENCE`, `NOT_APPLICABLE`, `NOT_COMPARABLE`, `CLARIFICATION_REQUIRED` |
| Находка | `CANDIDATE`, `NEGATIVE_VERIFIED`, `CONFIRMED_VIOLATION` (только инспектор), `SUSPICION` |

Реестр файлов (перечень ИД): `file_id`, `file_name`, `object_id`, `doc_stage`, `document_code`,
`revision`, `approval_status`, `approval_date`, `predecessor_id`, необязательно `sha256`,
`sheet_page_range`, `signature_status`. Без реестра пакет принимается, но каждый параметр
получает `CLARIFICATION_REQUIRED`. Лимиты: 50 МБ на файл, 200 МБ на пакет; формат — PDF
(DOCX и XML в этой версии не принимаются, отказ называет причину). Сбой проверки
повторяется до двух раз.

Протокол содержит раздельные таблицы: комплектность, кандидаты, подтверждённые,
проверенные отрицательные, гипотезы свободного поиска. Карточка кандидата: `finding_id`,
параметр, `expected/actual/delta`, по каждому источнику `file_id`, SHA-256, стадия, шифр,
редакция, статус утверждения, страница, bbox в [0;1], `approved_change_ref`, решение и
причина инспектора. Версии в каждом протоколе: `matrix_version`, `model_version`,
`dataset_version`, `input_manifest_hash`. При дозагрузке прежняя версия протокола
сохраняется.

Пример ответа — [docs/example-output.json](docs/example-output.json) (синтетические
документы, ответ модели задан сценарием; файл собирает настоящий код:
`scripts/make_example_output.py`). Параметр, по которому проверка не выполнилась, не
выдаётся за «нарушений нет»: `technical_status: "not_run"` и причина.

## Модели

| Назначение | Модель | Версия | Лицензия |
|---|---|---|---|
| Текст и изображения листов (VLM) | Qwen2.5-VL-7B-Instruct | ревизия весов — в `bundle/MANIFEST.txt` | Apache-2.0 |
| Сервер модели | vLLM (`vllm/vllm-openai`) | v0.28.0, образ закреплён дайджестом | Apache-2.0 |
| Распознавание сканов | Tesseract OCR, словари rus+eng | из Debian bookworm | Apache-2.0 |

Лицензии указаны по состоянию на подготовку комплекта; **перед сдачей сверить
с карточкой модели** на момент скачивания весов (из среды разработки карточка
была недоступна). Модель меняется переменными `NADZOR_MODEL_REPO`/`NADZOR_MODEL_DIR`
(скачивание) и `NADZOR_LOCAL_LLM_MODEL` (имя на сервере) без правки кода; при
смене нужно проверить, что её лицензия допускает коммерческое и государственное
использование — иначе она годится только для незачётного эксперимента.

Температура 0 и фиксированный seed сервера: повторный прогон на тех же
документах воспроизводим. Ответ, обрезанный по длине, считается сбоем проверки,
а не пустым результатом.

## Разработка

Нужны Python 3.11+ и Node.js 22. Модель — любой OpenAI-совместимый сервер внутри
контура (`NADZOR_LOCAL_LLM_URL`, `NADZOR_LOCAL_LLM_MODEL`, см. `.env.example`).

```bash
make install              # виртуальное окружение и зависимости
./scripts/start-all.sh    # движок на 8010 и интерфейс на 5173 одной командой
```

Без сервера модели разбор доходит до состава комплекта и честно сообщает, что
требования не извлекались. Без Tesseract сканы помечаются «движок распознавания
не установлен», а не «страница пуста».

## Что внутри

```
packages/backend/app/     движок: разбор, сверка, хранилища, LLM, HTTP API
packages/backend/tests/   тесты движка
frontend/src/             интерфейс: React 18, TypeScript, Vite, PWA
scripts/                  установка, запуск, диагностика, утилиты
scripts/offline/          офлайн-комплект: подготовка и запуск без Интернета
docker/                   образы backend (с Tesseract) и frontend
data/                     матрица параметров, реестр наблюдений, файловые базы
docs/                     документация, пример результата, журнал решений
models/  bundle/          веса модели и образы (поставляются отдельно, в git не идут)
```

Три файловые базы SQLite, разделённые осознанно: рабочее состояние прогонов,
оригиналы документов по отпечатку содержимого и память разбора страниц.
Для разработки PostgreSQL и Docker не нужны; официальный запуск — docker compose.

## Безопасность

Основная угроза — **инъекция инструкций через проверяемый документ**: документы
предоставляет поднадзорное лицо, заинтересованное в сокрытии нарушений. Любой
текст документа, попадающий в промпт, помечен как недоверенный ввод. Подробно —
[docs/threat-model.md](docs/threat-model.md).

Документы и их фрагменты не покидают контур: внешних сервисов нет, сетевой
запрет стоит перед каждым вызовом модели. Ключей и секретов у решения нет.
Реквизиты проверяемых объектов в репозиторий не идут.

## Правовая модель

Система формирует **гипотезы**, а не заключения. Ни одно юридически значимое
действие не совершается автоматически. Оговорки о статусе выводов в отчётах —
часть продукта, а не вежливость: без них отчёт читается как обвинение.

## Ограничения

- Без запущенной локальной модели разбор доходит до состава комплекта и честно
  сообщает, что требования не извлекались.
- Сверка комплекта в сотни листов — десятки и сотни обращений к модели и
  десятки минут работы. Прогресс виден, прогон останавливается кнопкой.
- Прототип CRM-витрины (дашборд, журналы, аудит, моки СУДИР и ИАИС ОГД) удалён
  из репозитория по решению владельца проекта: постановка задачи осталась в
  `CLAUDE.md`, кода больше нет.
- Все организации и физические лица в демонстрационных данных вымышлены.
