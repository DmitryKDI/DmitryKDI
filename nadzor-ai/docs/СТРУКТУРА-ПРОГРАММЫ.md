# Структура программы и последовательность действий

Прослежено по коду: порядок шагов ниже — тот, в котором они физически
выполняются. Читать после `CONTEXT.md`.

## 1. Главная идея

Проверка идёт **по матрице параметров ТЗ** (`data/parameter_catalog_v1_1.json`).
Каждый параметр — это вопрос «совпадает ли значение в ПД, РД и ИД»; модель
отвечает значениями с цитатами, а код проверяет, что каждая цитата реально
стоит на указанном листе, и сам строит координаты. Всё, что не удалось
проверить, остаётся видимым состоянием (`MISSING_EVIDENCE`,
`CLARIFICATION_REQUIRED`, `technical_status: not_run`), а не «нарушений нет».

## 2. Путь документа

```text
приём файла ─ app/main.py::ingest_pdf
  ├─ DOCX/XML → PDF (app/document_convert.py), тип по содержимому, XML без DTD
  ├─ лимиты размера и числа страниц, SHA-256, хранилище по отпечатку (app/file_store.py)
  ├─ тяжёлый том — части по весу, нумерация листов исходная (app/document_split.py)
  └─ фоновый разбор: текст страниц, OCR сканов (app/documents.py, app/local_ocr.py),
     память разбора по отпечатку (app/facts_store.py), раздел тома (app/classification.py)

метаданные тома ─ app/official_api.py::save_metadata (или реестр в /api/v1/documents/upload)
  стадия PD/RD/ID, шифр, редакция, статус утверждения, предшественник
```

## 3. Процесс проверки

`app/official_api.py::_execute` запускает `app/official_pipeline.py::run_official_analysis`:

1. **Комплектность и редакции** — `select_current_documents`: для каждого
   шифра актуальная редакция по цепочке замены и дате утверждения;
   неоднозначность — `CLARIFICATION_REQUIRED` у затронутых параметров.
2. **Сверка параметров матрицы** — параметры идут пачками
   (`NADZOR_OFFICIAL_BATCH_SIZE`) параллельно (`app/llm_runtime.py`). Для каждой
   пачки отбираются релевантные страницы всех трёх стадий, промпт начинается с
   правила о недоверенном тексте документа. Ответ проверяется
   `_verified_evidence`: цитата ищется на листе, bbox строится кодом.
3. **Графическая сверка** — листы ПД сопоставляются с листами РД/ИД
   (`app/lean_analysis_runtime.py`, `app/stateful_investigator.py`);
   графический кандидат без полной привязки к обеим сторонам — `SUSPICION`.
4. **Протокол** — `app/protocol.py::build`: статусы загрузки, сценарий, пять
   таблиц, карточки доказательств, версии и `input_manifest_hash`.

Сбой проверки повторяется до двух раз; остановка — `POST .../cancel`.
Дозагрузка, не меняющая состав актуальных редакций, переиспользует прежний
протокол без вызова модели.

## 4. Решения инспектора

`decide` — версионированное решение по кандидату (при отклонении обязателен
`reason_code`); `finalize` — только когда решены все кандидаты, после него
решения и дозагрузка закрыты; `unfinalize` — только администратор или
супервизор с причиной. Каждое действие пишется в журнал событий протокола
(`ProtocolEvent`).

## 5. Выгрузки

`app/protocol_export.py`: XML, DOCX, PDF (шрифт с кириллицей обязателен —
без него выгрузка отказывает, а не выдаёт нечитаемый файл). JSON — ответ API.
`POST /api/v1/inspection/{id}` — пакет только из финализированного протокола.

## 6. Модель

Одна точка обращения — `app/llm.py`. Адрес вне контура отклоняется до
отправки запроса. Ответы кэшируются по содержимому запроса, поэтому повторная
проверка того же комплекта воспроизводима.

## 7. Интерфейс

Вход — `pages/Login.tsx`; меню показывает экраны по роли пользователя.

- `pages/OfficialAnalysis.tsx` — загрузка томов и карточки метаданных, запуск,
  ход проверки, протокол с доказательствами на листе, решения, гипотезы
  свободного поиска (`FreeSearchCard.tsx`), «Завершить», выгрузки;
- `pages/Dashboard.tsx` — объекты с цветовой индикацией и фильтрами;
- `pages/Ml.tsx` — еженедельный отчёт, черновик GOLD-набора, выпуски, модели;
- `pages/Admin.tsx` — пользователи, матрица, нормативная база, логические
  правила, журнал аудита, целостность и резервные копии.

API-клиенты — `officialApi.ts`, `authApi.ts`, `adminApi.ts`.
