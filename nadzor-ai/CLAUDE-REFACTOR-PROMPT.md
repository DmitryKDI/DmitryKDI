# Мастер-промпт для Claude Code — НАДЗОР.ИИ

Ты работаешь над проектом `nadzor-ai` в репозитории `DmitryKDI/DmitryKDI`.
Цель — довести его до конкурсного продукта по задаче №10 Мосгосстройнадзора: ИИ-сервис сравнивает изменения между этапами проектирования, анализирует рабочую/исполнительную документацию и заранее формирует инспектору конкретные точки контроля с доказательствами.

## 1. Главный продуктовый принцип

Это НЕ чат с нейросетью и НЕ техническая панель LLM.
Это рабочее место инспектора строительного надзора.

Главный пользовательский результат:

`много документов → конкретные точки контроля → доказательства → действие инспектора`

Система не выносит юридически значимый вердикт автоматически. Формулировки уровня «нарушение установлено» запрещены. Используй: «потенциальное несоответствие», «требует проверки», «гипотеза», «подтверждено источниками». Решение принимает инспектор.

## 2. Что должно быть во фронтенде

Основное меню только такое:

1. Обзор
2. Документы
3. Точки контроля
4. Доказательства
5. Отчёты
6. История

Не возвращай в основной интерфейс:
- выбор провайдера LLM;
- выбор модели;
- API-ключи;
- token limits;
- concurrency;
- raw prompts;
- технические метрики запросов;
- storage/debug/version cards;
- внутренние названия pipeline-ступеней;
- настройки разработчика.

Если такие параметры нужны эксплуатации, они живут в backend/env/admin config, а не в рабочем месте инспектора.

### Обзор

Показывает только полезные KPI:
- проверено листов;
- критические/существенные точки;
- сколько требует проверки на объекте;
- сколько подтверждено несколькими источниками;
- изменения между стадиями/версиями.

Ниже — 5–7 приоритетных точек контроля.

### Документы

Две понятные зоны загрузки:
- ПД;
- РД / ИД.

Раздел документа определяется автоматически. Ручную коррекцию можно оставить только как вторичную функцию, если классификация ошиблась.

Главная кнопка: **«Запустить полный анализ»**.
Не заставляй инспектора понимать внутренний порядок `parse → compliance → vision → triangulation`.

### Точки контроля

Каждая карточка должна отвечать на четыре вопроса:
- что обнаружено;
- где;
- почему система обратила внимание;
- что сделать инспектору.

Приоритет: critical / major / minor.

### Доказательства

Слева исходный лист, справа проверяемый лист.
Показывай:
- лист/документ источника;
- что изменилось;
- почему важно;
- откуда вывод;
- рекомендацию инспектору.

Если возможно, синхронизировать zoom/pan и подсвечивать сравниваемую область.

### Отчёты

Формировать короткое задание на проверку, пригодное для печати/PDF:
- точка;
- приоритет;
- документ и лист;
- факт/расхождение;
- действие на объекте.

### История

Последние прогоны, статус, документы, дата, число найденных точек. Никаких prompt/debug payloads.

## 3. Модель ИИ

В пользовательском продукте один провайдер и одна модель:

- provider: `gigachat`
- default model: `GigaChat-3-Ultra`

Инспектор модель НЕ выбирает.

Допускается оставить техническую provider abstraction внутри backend только ради тестируемости/разработки, но публичный runtime и UI должны работать как GigaChat-first продукт.

Ключ загружается сервером из `secrets/` / переменных окружения. Секрет никогда не приходит во frontend.

## 4. Критическое ускорение LLM pipeline

### 4.1 Убрать head-of-line blocking

`parallel_map` должен поддерживать постоянное заполнение worker pool:
- как только ЛЮБОЙ future завершён, сразу запустить следующий item;
- наружу можно сохранить исходный порядок результатов;
- медленный первый запрос не должен оставлять остальные worker'ы пустыми.

Использовать `wait(..., return_when=FIRST_COMPLETED)` / эквивалент.

### 4.2 Не лечить скорость только concurrency

Количество одновременных запросов ограничивается тарифом GigaChat.
При 429 adaptive limiter снижает параллельность.
Не увеличивать concurrency без измерения.

Сначала уменьшить ЧИСЛО обращений.

### 4.3 Увеличить extraction batch

Сейчас `requirement_llm_extract.py` использует примерно 6000 символов на вызов — слишком мелко.

Сделать configurable budget:

`NADZOR_LLM_EXTRACTION_MAX_CHARS`

Стартовое значение для benchmark: **18000** символов.
Проверить также 12000 / 18000 / 24000 на эталонном датасете.

Лучший вариант — token-aware chunking с запасом на system prompt и JSON output. Если используется endpoint подсчёта токенов, его результат кэшировать; не превращать token count в новый узкий участок.

Пачка НИКОГДА не пересекает границу документа.
Номер страницы и document id сохраняются.

### 4.4 Persistent checkpoint каждого LLM результата

Успешный ответ модели нельзя терять при:
- рестарте backend;
- закрытии браузера;
- падении следующей пачки;
- сетевой ошибке после 40 минут работы.

Cache key обязан включать:
- provider/account identity без хранения секрета;
- model;
- operation;
- prompt version;
- document/source digest;
- input text/image digest;
- max output tokens.

Ответ сохранять локально в SQLite сразу после успешного вызова.

На повторном прогоне:
- готовые chunks брать из persistent cache;
- провайдеру отправлять только отсутствующие/неуспешные.

`RESULT_CACHE` должен переживать restart процесса.
`IMAGE_CACHE` можно оставить process-local, если remote file id имеет ограниченный lifetime.

### 4.5 Отдельный checkpoint состояния прогона

Следующий этап после persistent response cache: таблица `run_chunks`.
Для каждой пачки хранить:
- run_id;
- stage;
- chunk_index;
- source digest;
- status: pending/running/done/error;
- attempts;
- result reference;
- error category;
- timestamps.

После рестарта прогон должен продолжаться с pending/error chunks, а не начинаться с нуля.

Нельзя использовать частично сохранённый результат как «всё проверено».

### 4.6 Второстепенное обогащение не должно блокировать основной результат

Основной результат extraction сохранить сразу после извлечения требований.

Привязка к нормативам, enrichment профиля раздела и другие дополнительные операции не должны уничтожать уже готовый результат при своём падении.

Желательная схема:

`extract → checkpoint основной результат → enrichment → финальная сборка`

### 4.7 Параллелить независимое enrichment

`link_by_meaning` сейчас может идти batch-за-batch последовательно. Пачки независимы — использовать общий scheduler/limiter, сохраняя корректную адресацию по индексам.

## 5. Сопоставление листов

Главная задача качества и скорости — не смотреть одни и те же 3 листа под сотню требований.

Кандидаты нужно РАНЖИРОВАТЬ, а не фильтровать жёстким порогом.
Использовать совокупность сигналов:
- номер/тип помещения;
- этаж/отметка;
- дисциплина;
- sheet name/stamp;
- марки/позиции;
- редкие значимые слова;
- spatial/section hints, если доступны.

Бюджет vision должен тратиться на разнообразные высокорейтинговые кандидаты.

Никаких правил, заточенных под один тестовый комплект. `make check-generic` обязан проходить.

## 6. Версии документации

Долгосрочная модель продукта должна уйти от чистого `before/after` к:

`объект → этап → документ → редакция`

Поддержать переходы:
- ПД rev.N → ПД rev.N+1;
- ПД → РД;
- РД rev.N → РД rev.N+1;
- РД → ИД;
- ИД rev.N → ИД rev.N+1.

Существующий before/after engine можно оставить как внутренний механизм pairwise comparison, но UI и domain model не должны навсегда зависеть от двух корзин.

## 7. Надёжность

Обязательные правила:
- ошибка LLM ≠ «расхождений нет»;
- неполное покрытие ≠ «всё проверено»;
- отсутствие текста на чертеже ≠ «информации нет»;
- timeout одной пачки не роняет весь комплект;
- retry ограничен;
- Retry-After имеет верхний бюджет;
- prompt injection из проверяемого документа считается угрозой;
- секреты не логируются;
- текст документов не писать в технические логи без необходимости.

## 8. Метрики производительности

Для каждого прогона сохранять:
- wall-clock time;
- LLM requests;
- retries;
- 429;
- cache hits memory/persistent;
- average latency;
- input chars/tokens;
- chunks total/done/error;
- image uploads/reuse;
- этапы с длительностью.

Метрики нужны разработчику/логам, не основному UI инспектора.

## 9. Benchmark

Создать/использовать синтетический эталонный комплект ПД/РД/ИД с заранее известными расхождениями.

Считать минимум:
- precision;
- recall;
- число ложных находок;
- число пропусков;
- время прогона;
- число LLM calls;
- повторный прогон после restart: сколько реальных API calls потребовалось благодаря checkpoint.

Оптимизация считается успешной только если скорость выросла без заметной деградации recall.

## 10. Тесты перед завершением

Обязательно:

```bash
make test
make check-generic
cd frontend && npm run build
```

Добавить тесты на:
- parallel scheduler не простаивает из-за медленного первого future;
- порядок результатов сохраняется;
- persistent result cache переживает новый instance/process simulation;
- повторный extraction не вызывает provider для уже сохранённых chunks;
- 429 снижает нагрузку;
- ошибки chunk не превращаются в пустой «успех»;
- новый frontend собирается без TypeScript ошибок.

Если старые тесты требуют отсутствующие локальные PDF, отделить это от реальной регрессии и явно зафиксировать.

## 11. Критерий готовности

Инспектор должен уметь:

1. открыть приложение;
2. загрузить ПД и РД/ИД;
3. нажать одну основную кнопку;
4. уйти на другой экран/перезагрузить страницу;
5. вернуться и увидеть продолжающийся или завершённый прогон;
6. при рестарте backend не потерять уже оплаченные успешные LLM chunks;
7. получить короткий список точек контроля;
8. открыть доказательство по конкретной точке;
9. сформировать задание на выезд/отчёт.

Если для выполнения этого сценария инспектор должен выбирать модель, concurrency, токены, prompt или разбираться во внутренних стадиях pipeline — UX считается неготовым.
