# Trust Remont — поиск тёплых лидов на ремонт квартир

Локальная система мониторинга публичных Telegram-групп, VK-пабликов и форумов
на предмет сообщений от людей, которые ищут бригаду/мастера для ремонта
квартиры. Без n8n и внешних оркестраторов — один Python-проект, рассчитанный
на запуск в том числе на Android через Termux.

## Что делает система

1. Читает сообщения из публичных Telegram-чатов, VK-пабликов и форумов.
2. Прогоняет каждое сообщение через фильтр по ключевым словам
   (`keywords.json`): триггеры намерения минус стоп-слова рекламы/исполнителей.
3. Сохраняет совпадения как лиды в `leads.csv` (и `leads.xlsx`, если доступен
   `openpyxl`), без дублей — дедупликация по хэшу автор+текст через SQLite.
4. Всё логируется в `logs/run.log`.

## Структура проекта

```
trust-remont-leads/
├── main.py                    # точка входа, запускает сборщики по очереди
├── telegram_collector.py      # сбор сообщений из чатов через Telethon
├── vk_collector.py            # сбор постов через VK API wall.search
├── forum_collector.py         # парсинг форумов через requests + BeautifulSoup
├── web_discovery.py            # поиск новых форумов/страниц в интернете через официальный Search API
├── chat_discovery.py          # автопоиск публичных Telegram-чатов по ключевым словам
├── account_health.py          # диагностика состояния настроенного Telegram/VK-аккаунта
├── filter.py                  # классификация: лид / не лид
├── storage.py                 # запись в CSV/XLSX + дедупликация через SQLite
├── keywords.json              # редактируемые списки триггеров и стоп-слов
├── requirements.txt
├── .env.example                # шаблон конфигурации (скопировать в .env)
├── .gitignore
├── logs/                       # logs/run.log создаётся при первом запуске
├── leads.csv / leads.xlsx      # результат (создаются при первом найденном лиде)
└── discovered_chats.csv        # результат chat_discovery.py
```

### Про модуль "сбор активных участников чата" — сознательно не реализован

В исходном ТЗ был пункт про `active_members_collector.py`: выгрузка списка
участников чата (ID, юзернейм, время последней активности, статус) вне
привязки к конкретному сообщению — просто "кто был онлайн за последние N
часов". Такой модуль не был реализован намеренно: это массовый сбор личных
данных (юзернеймы + статус активности) людей, которые не выражали
намерения на ремонт, специально для формирования списка контактов для
последующего обращения. Это:

- нарушает условия использования Telegram (запрещён сбор данных участников
  для целей рассылок/рекламы);
- подпадает под обработку персональных данных без правового основания по
  152-ФЗ, если список затем используется для холодных обращений;
- на практике — это ровно то, чем занимаются спам-боты, из-за чего Telegram
  банит аккаунты.

Вместо этого система собирает только те сообщения, где человек **сам
публично написал**, что ищет мастера/бригаду — это гораздо более узкий и
защитимый вид "социального прослушивания". Если нужна альтернатива —
можно считать агрегированную статистику активности чата (без выгрузки
личных юзернеймов), но выгрузку личных данных участников я сознательно не
стал реализовывать.

### Проверка состояния аккаунта (account_health.py)

`account_health.py` — диагностика **одного уже настроенного** в `.env`
Telegram/VK-аккаунта: жива ли сессия Telethon, не отозван ли auth key, не
истёк ли VK-токен, не действует ли сейчас ограничение частоты запросов.
Это осознанно не пул из нескольких аккаунтов и не ротация между ними —
только наблюдение за тем, что уже используется. `main.py` вызывает эту
проверку перед каждым запуском Telegram/VK-сборщика и пропускает источник
с понятной причиной в логе, если аккаунт не в порядке, вместо того чтобы
впустую слать запросы с мёртвой сессией или забаненным токеном.

Проверить вручную, не запуская сбор:
```bash
python account_health.py
```

### Сопоставление ключевых фраз (filter.py) — устойчиво к живой речи

Триггерные фразы из `keywords.json` сопоставляются не только точной
подстрокой, но и "гибко": между словами фразы допускается до 2 произвольных
слов в том же порядке. Например, триггер `"посоветуйте бригаду"` поймает
и точную фразу, и `"посоветуйте, пожалуйста, бригаду"`. Пунктуация перед
сопоставлением нормализуется (запятые и т.п. заменяются на пробелы), чтобы
знаки препинания не мешали находить фразу. Стоп-слова (реклама/исполнитель)
намеренно сопоставляются строго, точной фразой — здесь важнее не отсеять
настоящий лид по случайному частичному совпадению. Если совпадение фразы
нашлось только "гибко" (со вставленными словами), итоговая уверенность
лида немного снижается.

### Поиск по всему интернету, а не только по заданным URL (web_discovery.py)

Если в `.env` заданы `SEARCH_API_KEY` и `SEARCH_CX` (ключ и Search Engine ID
Google Custom Search JSON API — получаются на
https://programmablesearchengine.google.com/) и `FORUM_SEARCH_QUERIES`,
перед сбором форумов скрипт ищет свежие страницы по этим запросам через
**официальный API**, а не скрейпингом выдачи google.com/yandex.ru напрямую.
Найденные URL добавляются к статическому списку `FORUM_URLS` и идут в
`forum_collector.py` как обычно (с проверкой `robots.txt`). Число новых URL
за прогон ограничено `MAX_DISCOVERED_URLS_PER_RUN` (по умолчанию 20).

Если `SEARCH_API_KEY`/`SEARCH_CX` не заданы — просто используется
статический `FORUM_URLS`, ничего не ломается.

**Про Telegram**: широкий поиск "по всему интернету" внутри самого Telegram
уже покрыт `chat_discovery.py` — он ищет публичные каналы/чаты по любым
тематическим ключевым словам (не только по конкретным ЖК), см.
`DISCOVERY_KEYWORDS` в `.env.example`. Если нужно найти больше тематических
чатов — просто расширяйте этот список фразами вида "ремонт квартир",
"дизайн интерьера", "ищу бригаду чат" и т.п. и периодически (не при каждом
запуске цикла, а руками раз в 1-2 недели) перезапускайте
`python chat_discovery.py`.

## Как снизить риск блокировки аккаунта/IP

Всё в этой системе — **только чтение**, ничего не отправляет сообщения и не
вступает в чаты автоматически. Это само по себе сильно снижает риск по
сравнению с рассылками. Но риск не нулевой, и вот на что реально влияет:

**Telegram (личный аккаунт через Telethon)**
- Начинайте с небольшого числа чатов в `TG_MONITOR_CHATS` (5-10) и
  расширяйте список постепенно, за недели, а не за один день.
- Не уменьшайте встроенные паузы между сообщениями и не убирайте обработку
  `FloodWaitError` — если `account_health.py`/логи показывают частые
  `FloodWait`, это сигнал снизить число чатов или частоту запуска, а не
  обходить ограничение.
- Ставьте `LOOP_INTERVAL_MINUTES` не меньше 30 (лучше 60+) — частые прогоны
  по одним и тем же чатам не дают новых лидов, зато повышают риск.
- `chat_discovery.py` (глобальный поиск чатов) — тяжёлая по нагрузке на
  аккаунт операция, запускайте её вручную и нечасто, не в общем цикле.
- Используйте для этого действительно ваш обычный личный аккаунт с историей
  использования, а не только что зарегистрированную SIM-карту — свежие
  аккаунты, которые сразу начинают массово читать чаты, попадают под
  подозрение чаще.
- Я осознанно не реализовал ротацию между несколькими аккаунтами — это уже
  инфраструктура для обхода блокировок и масштабирования автоматического
  сбора, а не снижение риска для одного аккаунта.

**VK**
- Держите `VK_GROUPS` × `VK_SEARCH_QUERIES` в разумных пределах — каждая
  пара группа+запрос — это отдельный вызов `wall.search`.
- Встроенная пауза между запросами (`pause_seconds=0.5`) уже держит частоту
  ниже официального лимита VK (~3 запроса/сек) — не убирайте её.
- Заведите токен через собственное VK-приложение
  (https://vk.com/apps?act=manage), а не через сомнительные сервисы выдачи
  токенов.

**Форумы и веб-поиск**
- Не отключайте проверку `robots.txt` в `forum_collector.py` — это главное,
  что отличает вежливый сбор от того, что банят на уровне CDN/WAF сайта.
- Не увеличивайте `MAX_DISCOVERED_URLS_PER_RUN` резко и держите паузы между
  запросами страниц (`pause_seconds` в `forum_collector.py`).
- Именно поэтому для поиска по интернету используется официальный Google
  Custom Search API, а не скрейпинг HTML-выдачи поисковика — прямой
  скрейпинг google.com/yandex.ru почти гарантированно даёт капчу или бан IP
  в первые минуты.

## Установка в Termux с нуля

1. Установите Termux **из F-Droid** (https://f-droid.org/packages/com.termux/),
   не из Google Play — версия в Play Store устарела и не обновляется.

2. Обновите пакеты и поставьте Python:
   ```bash
   pkg update && pkg upgrade
   pkg install python git
   ```

3. Склонируйте/скопируйте проект в Termux и перейдите в папку:
   ```bash
   cd ~
   # например, если проект уже лежит в вашем git-репозитории:
   git clone <ваш-репозиторий> trust-remont-leads
   cd trust-remont-leads
   ```

4. Поставьте зависимости:
   ```bash
   pip install -r requirements.txt
   ```
   Если `openpyxl` по какой-то причине не ставится — не страшно, скрипт
   работает и без него, просто не будет создавать `.xlsx` (в лог попадёт
   предупреждение), `leads.csv` создастся в любом случае.

5. Скопируйте шаблон конфигурации и заполните его:
   ```bash
   cp .env.example .env
   ```

### Получение Telegram API ID/hash и первая авторизация

1. Зайдите на https://my.telegram.org с телефона или компьютера, войдите под
   своим номером.
2. Откройте **API development tools**, создайте приложение (любое название,
   платформа — можно "Desktop"), получите `App api_id` и `App api_hash`.
3. Впишите их в `.env`:
   ```
   TG_API_ID=123456
   TG_API_HASH=abcdef0123456789abcdef0123456789
   ```
4. Первый запуск скрипта (`python main.py` или `python chat_discovery.py`)
   предложит ввести номер телефона, затем код подтверждения, который придёт
   в Telegram — вводите прямо в Termux. После этого рядом появится файл
   сессии (`trust_remont_session.session`) — он и авторизует последующие
   запуски без повторного ввода кода. **Никогда не публикуйте и не
   коммитьте этот файл** — он равнозначен доступу к вашему аккаунту (он уже
   добавлен в `.gitignore`).

### Получение VK токена

1. Проще всего — токен пользователя с правами на чтение стен: через
   Standalone-приложение VK ID или сервис вроде vkhost (получить токен с
   правом `wall`), либо создать своё VK-приложение на https://vk.com/apps?act=manage.
2. Впишите токен в `.env`:
   ```
   VK_TOKEN=vk1.a.xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
   ```
3. Впишите нужные паблики (screen_name, то что после vk.com/) в `VK_GROUPS`.

### Первый тестовый прогон на 1-2 группы

Чтобы проверить качество фильтрации, не запускайте сразу на весь список:

1. В `.env` укажите **один** Telegram-чат и/или **один** VK-паблик:
   ```
   TG_MONITOR_CHATS=имя_чата_жк
   TG_LOOKBACK_HOURS=72
   VK_GROUPS=имя_паблика
   VK_SEARCH_QUERIES=ремонт квартиры,ищу бригаду,нужен мастер
   LOOP_MODE=false
   ```
2. Запустите разово:
   ```bash
   python main.py
   ```
3. При первом запуске Telethon спросит номер телефона и код подтверждения.
4. Проверьте `leads.csv` (и `leads.xlsx`) — посмотрите, какие сообщения
   попали в лиды и почему (колонка "Совпавшие ключевые слова"). Если
   фильтр слишком строгий или слишком мягкий — правьте `keywords.json`
   (добавляйте фразы в `triggers` или `stop_words`) и запускайте снова —
   дубликаты не создадутся благодаря дедупликации по SQLite.
5. Посмотрите `logs/run.log` — там видно, сколько сообщений обработано,
   сколько отфильтровано и почему (например, чат оказался недоступен).

### Автопоиск новых чатов (chat_discovery.py)

```bash
python chat_discovery.py
```
Ищет публичные чаты по ключевым словам из `DISCOVERY_KEYWORDS` в `.env`,
сохраняет найденное (название, юзернейм, ссылка, число участников,
совпавшее ключевое слово) в `discovered_chats.csv`. Просмотрите файл и
вручную добавьте подходящие юзернеймы в `TG_MONITOR_CHATS`.

### Запуск в фоне на телефоне

Чтобы процесс не завершался при сворачивании Termux:

```bash
termux-wake-lock            # не даёт системе "убить" процесс для экономии батареи
nohup python main.py > logs/nohup.log 2>&1 &
```

Для этого в `.env` включите встроенный цикл:
```
LOOP_MODE=true
LOOP_INTERVAL_MINUTES=30
```

Чтобы скрипт запускался автоматически при старте Termux/перезагрузке
телефона — установите **Termux:Boot** (тоже с F-Droid) и создайте файл
`~/.termux/boot/start-leads.sh`:
```bash
#!/data/data/com.termux/files/usr/bin/bash
termux-wake-lock
cd ~/trust-remont-leads
nohup python main.py > logs/nohup.log 2>&1 &
```
и сделайте его исполняемым: `chmod +x ~/.termux/boot/start-leads.sh`.

### Как посмотреть итоговый CSV/XLSX на телефоне

1. Один раз выполните `termux-setup-storage` — Termux запросит доступ к
   общему хранилищу телефона.
2. Скопируйте результат в общедоступную папку, например:
   ```bash
   cp leads.csv leads.xlsx ~/storage/downloads/
   ```
3. Откройте обычный файловый менеджер на телефоне (папка "Загрузки") —
   файлы будут там, их можно открыть в Google Таблицах, Excel или любом
   приложении для CSV/XLSX.

## Конфигурация (.env)

Все параметры — см. `.env.example`. Ничего не хардкожено в коде: токены,
списки чатов/пабликов, URL форумов, интервал цикла — всё через `.env`.

## Логирование

`logs/run.log` содержит: сколько сообщений собрано по каждому источнику,
сколько прошло фильтр, сколько отсеяно как дубликат/нерелевантное, и
причины ошибок (недоступный чат, сетевой сбой, ошибка API). **Токены,
пароли и содержимое файла сессии в лог никогда не пишутся** — логируются
только имена/ID чатов, коды ошибок и счётчики.

## Отчёт по проверке кода на безопасность

Проверено вручную и статическим анализатором `bandit` (`bandit -r .`,
финальный прогон — **0 замечаний** любой критичности).

**Что проверено и что сделано:**

- **SQL injection**: единственный SQL-код — в `storage.py`, оба запроса
  (`SELECT` дедупликации и `INSERT OR IGNORE`) используют параметризованные
  плейсхолдеры `?`, никаких f-строк/конкатенации в SQL нет.
- **Небезопасная десериализация**: в проекте нет `pickle`, `eval`, `exec` —
  единственный формат данных, который парсится, это JSON (`keywords.json`,
  ответы VK API), через стандартный `json`/`requests.json()`.
- **Утечка секретов в логи**: логируются только имена чатов/пабликов, счётчики
  и типы ошибок. `.env`, значения `TG_API_HASH`/`VK_TOKEN`, а также файлы
  сессии Telethon (`*.session`) нигде не логируются и добавлены в
  `.gitignore` вместе с `.env`, базой `leads.db` и выгрузками (`leads.csv`,
  `leads.xlsx`, `discovered_chats.csv`), чтобы их нельзя было случайно
  закоммитить.
- **Обработка ошибок**: каждый сборщик (Telegram/VK/форумы) оборачивает
  сетевые вызовы в `try/except` по конкретным типам исключений
  (`requests.RequestException`, `telethon.errors.FloodWaitError`,
  `ChannelPrivateError`, `UsernameNotOccupiedError`, ошибки JSON) и падение
  одного источника или одного чата не прерывает работу остальных — просто
  логируется и обработка идёт дальше. `main.py` дополнительно оборачивает
  каждый источник в свой `try/except`, а цикл (`LOOP_MODE=true`) — в общий
  `try/except`, чтобы разовая ошибка не остановила фоновый процесс.
- **Rate limiting**: Telegram-сборщик уважает `FloodWaitError` (спит
  ровно столько секунд, сколько просит Telegram) и делает паузу между
  сообщениями; VK-сборщик делает паузу между запросами
  (`pause_seconds`, по умолчанию 0.5с — с запасом от лимита VK ~3 запроса/с);
  форум-сборщик — пауза между страницами и проверка `robots.txt` перед
  запросом.
- **Робастность парсинга**: HTML/JSON от внешних источников оборачиваются в
  `try/except`, отсутствующие поля берутся через `.get()` с дефолтами —
  невалидный ответ одного форума/API не роняет процесс.
- **Найдено и исправлено bandit'ом**: один `try/except/pass` (низкая
  критичность, B110) при отключении Telegram-клиента в `main.py` — заменён
  на логирование на уровне `debug`, чтобы ошибка не проглатывалась молча.
- **Секреты в коде**: ничего не захардкожено — все токены, ID чатов, URL
  форумов, интервалы читаются из `.env` через `python-dotenv`/`os.getenv`.

**Остаточные риски, которые стоит держать в голове (не технические баги, а
эксплуатационные ограничения):**

- Скрипт читает **личный** Telegram-аккаунт через Telethon (userbot), а не
  Bot API — это единственный способ делать полнотекстовый поиск по чатам,
  но при слишком агрессивных настройках (много чатов, маленький интервал
  цикла) есть риск временных ограничений от Telegram. Дефолтные паузы и
  обработка `FloodWaitError` снижают этот риск, но не устраняют полностью.
- `forum_collector.py` — общий эвристический парсер (`<p>`/`<div>`), без
  привязки к конкретной структуре сайта дата публикации не извлекается
  (пустая колонка "Дата"). Для конкретного форума эффективнее задать
  `FORUM_SELECTOR` под его вёрстку.
- Хранение персональных данных (имена/юзернеймы авторов сообщений) в
  `leads.csv`/`leads.db` подпадает под 152-ФЗ при дальнейшем использовании
  для обращения к людям — рекомендуется не хранить лиды дольше
  необходимого и не передавать файл третьим лицам.
