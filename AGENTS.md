## 1. Назначение проекта

**НАДЗОР.ИИ** — ИИ-сервис для инспектора строительного надзора (задача
города № 10). Он сверяет проектную (ПД), рабочую (РД) и исполнительную (ИД)
документацию объекта по матрице параметров ТЗ и готовит протокол с
доказательствами до выезда на объект.

Ключевое ограничение продукта: система выдаёт **гипотезы, а не заключения**.
Нарушение подтверждает только инспектор (`CONFIRMED_VIOLATION`). Формулировки
в коде и интерфейсе обязаны это удерживать — см. правило Г.10 в разделе 5.

Официальный прогон идёт **офлайн, в закрытом контуре**: модель только
локальная, внешних API нет, запуск — одной командой `docker compose up`.

## 4. Архитектура

### Процесс проверки

1. **Приём** (`main.py::ingest_pdf`, `api_v1.py`) — PDF, DOCX, XML; тип по
   содержимому, DOCX/XML приводятся к PDF, XML с DTD отклоняется; лимиты,
   SHA-256, хранилище по отпечатку, тяжёлый том режется на части по весу.
   Разбор страниц и OCR — фоновой задачей.
2. **Метаданные тома** — стадия, шифр, редакция, статус утверждения,
   предшественник: карточкой в интерфейсе или реестром в `/api/v1`.
3. **Сверка** (`official_pipeline.py`) — актуальные редакции по шифру →
   параметры матрицы пачками → проверка цитат и координат кодом → графическая
   сверка листов → протокол (`protocol.py`).
4. **Решения инспектора и финализация** (`official_api.py`) — версионированные
   решения, `reason_code` при отклонении, «Завершить» только при решённых
   кандидатах, отмена финализации — администратор/супервизор с причиной.
5. **Выгрузки** (`protocol_export.py`) — JSON, XML, DOCX, PDF; пакет для
   внешней системы — только из финализированного протокола.

### Базы

| Файл | Модуль | Что хранит |
|---|---|---|
| `nadzor.db` | `db.py` | документы, процессы, протоколы, решения, журнал событий |
| `file_store.db` | `file_store.py` | оригиналы файлов по SHA-256 |
| `facts_store.db` | `facts_store.py` | разбор страниц по отпечатку (восстановим пересчётом) |

В docker compose все базы лежат в именованном томе `nadzor-state` (`/app/state`).

### Модель

Одна точка обращения — `llm.py`. Адрес вне контура (не loopback, не частная
сеть, не имя сервиса compose) отклоняется до отправки запроса.

## 5. Обязательные правила разработки

Полный текст — `nadzor-ai/CLAUDE.md`, раздел 0. Здесь то, что нарушается чаще
всего и проверяется машиной.

### Г.10 — молчание никогда не значит «чисто»

Невыполненная проверка обязана быть названа невыполненной
(`technical_status: not_run`, `MISSING_EVIDENCE`, `CLARIFICATION_REQUIRED`).
Технический сбой никогда не превращается в «нарушений нет».

### Правило 8 — всё общее для любой документации

Пример, на котором идёт работа, **не попадает ни в код, ни в комментарии, ни в
промпты, ни в инструкции**. Наблюдение о конкретном разделе — это данные с
честным статусом `n=`, а не строчка в механике. Проверяется машиной:
`make check-generic`.

### Порядок любой правки

1. Любая новая числовая константа объявляется в
   `test_constants_are_declared.py` одним из видов: БЮДЖЕТ, ПРАВИЛО ЯЗЫКА,
   ГЕОМЕТРИЯ/ФОРМАТ, ПОДОГНАНО с честным `n=`.
2. Порог из одного комплекта — не правило, а наблюдение.
3. Не отсеивай там, где можно ранжировать.
4. Проверяй правку на документе, которого не видел.

### Данные объекта и контур

- Реальные документы и реквизиты проверяемых объектов (шифр, организация,
  маркировка тома, текст) в репозиторий не идут **вообще**, включая тесты и
  журнал. Тесты строят свои документы в памяти при прогоне.
- Документы не отправляются во внешние сервисы. Никаких облачных моделей,
  ключей и внешних OCR.
- Текст документа — недоверенный ввод: каждый промпт начинается с
  `UNTRUSTED_INPUT_RULE` (`vision.py`).

### Дисциплина журнала

Новая находка = короткое правило (3–4 строки) в `CLAUDE.md`, полный разбор —
в `docs/PRILOZHENIE-G-ISTORIYA.md` (только дописывается в конец).

## 6. Соглашения по коду

- **Комментарии и документация — на русском. Код и имена — на английском.**
- Комментарий объясняет **почему**, а не что.
- Модули общаются через публичные функции; приватное — с `_` в начале.
- Имена файлов: `snake_case.py` в движке, `PascalCase.tsx` для компонентов,
  `camelCase.ts` для остального во фронте.
- Длина строки — 100 (`ruff`).
- Тесты называются по проверяемому поведению и печатают `print("OK: …")`.

## 7. Команды

Все — из каталога `nadzor-ai/`.

```bash
make install              # .venv и npm-зависимости
./scripts/start-all.sh    # движок на 8010 и интерфейс на 5173
make test                 # тесты движка
make check-generic        # обязательная проверка перед коммитом
make lint                 # линтер
make openapi              # выгрузка схемы OpenAPI 3.0 в docs/openapi.json
cd frontend && npm run build && npm test
```

Официальный запуск: `docker compose up -d` (на стенде без Интернета —
`scripts/offline/load_bundle.sh`).

заключение») из протокола, интерфейса и промптов.

## 9. Известные ограничения

- Качество модели проверяется только на стенде с GPU.
- Шаблон протокола из Приложения № 2 к ТЗ не предоставлен: протокол собран по
  тексту ТЗ.
- Передача во внешнюю систему выключена, пока не задан `NADZOR_RIN_URL`
  (`external_sync.py`): тогда пакет только формируется (`LOCAL_ONLY`).
- Сверка комплекта в сотни листов — десятки и сотни обращений к модели. Это не
  зависание: ход виден по этапам, проверка останавливается кнопкой.
