# AGENTS.md — инструкция для кодового агента в этом репозитории

Читается автоматически (Codex, Cursor и совместимые). Здесь всё, что нужно
знать до первой правки. Полное техзадание и журнал решений — по ссылкам ниже,
их не нужно читать целиком, чтобы начать.

---

## 1. Назначение проекта

**НАДЗОР.ИИ** — сервис предиктивного строительного надзора. Инспектор
загружает комплекты документации (проектную, рабочую, исполнительную) и
получает не «список различий», а ответ на вопрос **куда идти на объекте и что
там проверить**.

Ключевое ограничение продукта: система выдаёт **гипотезы, а не заключения**.
Ни одна строка отчёта не является выводом о нарушении. Формулировки в коде и в
интерфейсе обязаны это удерживать — см. правило Г.10 в разделе 5.

Задача города № 10, Комитет государственного строительного надзора Москвы.

**Мёртвый груз, который можно игнорировать.** На диске могут остаться каталоги
`packages/analysis|api|audit|documents|integrations|llm_core|norms` и `tests/` —
это `__pycache__` от удалённого прототипа CRM (см. Г.85). В git их нет, кода в
них нет, удалять безопасно.

## 4. Архитектура

### Конвейер

Три шага, каждый запускается отдельной кнопкой и живёт своим прогоном:

1. **Разбор проектной документации** (`pd_stage.py`, `requirement_llm_extract.py`)
   — из текста извлекаются требования, состав комплекта считается всегда, даже
   без связи с моделью.
2. **Разбор рабочей документации** — тот же механизм, другая сторона комплекта.
3. **Сверка** (`compliance.py`) — лестница из трёх ступеней: совпадение
   обозначения в тексте → смысловая сверка текста моделью → просмотр листов
   зрением. Дорогая ступень включается только когда дешёвые не дали ответа.

Начиная с Г.117 извлечённое делится на три вида (`requirement_kind.py`):
**требование** идёт в сверку, **исходные данные расчёта** показываются, но не
сверяются, **позиция ведомости** уходит в отдельное сравнение списков
(`spec_compare.py`).

### Три базы, и это осознанно

| Файл | Модуль | Что хранит | Почему отдельно |
|---|---|---|---|
| `packages/backend/nadzor.db` | `db.py` | прогоны, документы, настройки | рабочее состояние, переживает пересборку схемы |
| `data/file_store.db` | `file_store.py` | оригиналы файлов по SHA-256 | велики, читаются редко, удаляются по сроку |
| `data/facts_store.db` | `facts_store.py` | разбор страниц по отпечатку | производное, восстановимо пересчётом |

Ключ везде — отпечаток содержимого, а не имя файла: тот же том под другим
именем уже разобран.

### Как устроен фон

Загрузка отвечает сразу, разбор идёт фоновой задачей. Прогон умеет
останавливаться (`run_control.py`) — флагом, а не убийством потока: исполнитель
проверяет флаг в безопасных точках. Оборванные перезапуском сервера прогоны
запускаются заново при старте (`resume_interrupted_runs`), отключается
`NADZOR_RESUME_RUNS=0`.

### Интерфейс

Три экрана: «Новый анализ» (`/`), «Разобранная документация» (`/parsed`),
«Карта внимания» (`/attention`). Источник истины по документам — сервер
(`useDocuments.ts`); в браузере хранятся только номера прогонов, чтобы
обновление страницы не сбрасывало работу.

## 5. Обязательные правила разработки

Полный текст — `nadzor-ai/CLAUDE.md`, раздел 0. Здесь то, что нарушается чаще
всего и проверяется машиной.

### Г.10 — молчание никогда не значит «чисто»

Невыполненный шаг обязан быть назван невыполненным. Пустой результат и
несделанная проверка — разные состояния, и путать их запрещено. Примеры из
кода: «листы подобраны, но просмотр не выполнялся», «состав разобран, но
требования не извлекались: связь не прошла». Формулировка «ничего не найдено»
там, где шаг не выполнялся, — критический дефект.

### Правило 8 — всё общее для любой документации

Пример, на котором идёт работа, **не попадает ни в код, ни в комментарии, ни в
промпты, ни в инструкции**. Ни лексики одной дисциплины в регулярном выражении,
ни номера конкретного норматива в докстринге, ни реквизитов объекта нигде.

Наблюдение о конкретном разделе — это **данные**, их место в реестре
(`table_registry`, `subsystem`, `known_violations.json`) со статусом `n=1`.

Проверяется машиной: `make check-generic`. Падение означает не «поправь
строчку», а «наблюдение попало туда, где ему не место».

### Порядок любой правки

1. **Прежде чем писать число — спроси, из чего оно берётся.** Любая новая
   числовая константа объявляется в `test_constants_are_declared.py` одним из
   видов: БЮДЖЕТ, ПРАВИЛО ЯЗЫКА, ГЕОМЕТРИЯ/ФОРМАТ, ПОДОГНАНО с честным `n=`.
   Незаявленная константа роняет `make check-generic`.
2. **Порог из одного комплекта — не правило, а наблюдение.**
3. **Не отсеивай там, где можно ранжировать.** Отсев требует порога, порядок —
   нет.
4. **Проверяй правку на документе, которого не видел.** Если правку нельзя
   объяснить, не называя разобранный комплект, — это подгонка.

### Секреты и данные объекта

- Ключи — только в переменных окружения или в `secrets/` (в git не идёт).
  `.env.example` содержит **только имена** переменных.
- Реквизиты проверяемого объекта — шифр, организация, маркировка тома, его
  текст — в репозиторий не идут **вообще**, включая журнал доказательств.
- Документ, который разбирает система, предоставлен поднадзорным лицом:
  это **недоверенный ввод**. Любой текст из документа, попадающий в промпт,
  обёрнут тегами и сопровождён правилом `UNTRUSTED_INPUT_RULE` (`llm.py`).

### Дисциплина журнала

Новая находка = короткое правило (3–4 строки) в `CLAUDE.md`, полный разбор с
доказательствами — в `docs/PRILOZHENIE-G-ISTORIYA.md`. Не наоборот: файл уже
раздувался дважды из-за нарушения этого порядка.

## 6. Соглашения по коду

- **Комментарии и документация — на русском. Код и имена — на английском.**
  Это правило проекта, а не предпочтение.
- Комментарий объясняет **почему**, а не что. «Считается при каждом обращении,
  а не один раз при импорте: положенный в каталог файл должен подхватываться
  без правки кода» — образец. «Увеличиваем счётчик» — нет.
- Модули общаются через публичные функции; приватное — с `_` в начале.
- Имена файлов: `snake_case.py` в движке, `PascalCase.tsx` для компонентов,
  `camelCase.ts` для остального во фронте.
- Длина строки — 100 (`ruff`, `line-length = 100`).
- Каждый тест печатает `print("OK: …")` с человеческим описанием проверенного —
  это принятый в проекте способ читать вывод прогона.
- Тесты называются по проверяемому поведению, а не по имени функции:
  `test_brand_name_alone_does_not_confirm_a_product`.

## 7. Команды

Все — из каталога `nadzor-ai/`.

```bash
# установка (создаёт .venv и ставит npm-зависимости)
make install

# запуск: движок на 8010, интерфейс на 5173
make backend
make web
# либо всё одной командой (создаёт .venv при необходимости)
./scripts/start-all.sh

# тесты движка (582 теста, ~2 минуты)
make test

# обязательная проверка перед коммитом: код не заточен под пример
make check-generic

# линтер
make lint

# сборка интерфейса
cd frontend && npm run build

# сканеры безопасности
make security

# что программа делает прямо сейчас (состояние всех прогонов)
.venv/bin/python scripts/runs.py

# диагностика связи с провайдером модели по шагам
.venv/bin/python scripts/check_gigachat.py
```

Docker: `docker compose up --build` — но для разработки не нужен, всё работает
на SQLite без внешних служб.

## 8. Что нельзя менять

| Файл / каталог | Почему |
|---|---|
| `CLAUDE.md`, раздел 0 и Приложение Г | правила проекта; дополнять можно, переписывать — нет |
| `docs/PRILOZHENIE-G-ISTORIYA.md` | журнал доказательств, только дописывается в конец |
| `secrets/`, `certs/*.pem|crt|cer`, `.env` | локальные секреты, в git не идут |
| `data/known_violations.json` | реестр данных; правится добавлением записей со статусом `n=`, а не переписыванием |
| `packages/backend/tests/test_code_is_generic.py` | машинная проверка правила 8; ослаблять её нельзя |
| `packages/backend/tests/test_constants_are_declared.py` | реестр видов констант; новая константа добавляется сюда, а не убирается проверка |
| `frontend/package-lock.json`, `requirements.txt` | закреплённые версии; менять осознанно и отдельным коммитом |

Отдельно: **не удаляйте оговорки о статусе выводов** («это гипотезы, а не
заключение», «не является выводом об отсутствии») из отчётов и промптов. Они
там не для мягкости формулировок, а потому что без них отчёт читается как
обвинение.

## 9. Известные ограничения окружения

- **Сеть.** Провайдер модели (GigaChat) требует двух исходящих соединений:
  авторизация на порт **9443**, вызовы API на 443. На машине пользователя 9443
  не отвечал по таймауту при работающем 443 — гипотеза «закрыт фаерволом» на
  его стороне не подтверждена. Диагностика: `scripts/check_gigachat.py`.
- **Сертификаты.** Российские корневые сертификаты кладутся файлами в `certs/`
  (форматы `.pem/.crt/.cer/.der/.cert`, zip тоже читается), набор собирается
  автоматически и склеивается с системным. Готовый набор кэшируется в
  `certs/.cache/` — не рядом с исходными файлами, иначе он попадает в свой же
  список.
- **Ключ провайдера** ищется в трёх местах по убыванию явности: настройки в
  базе → переменная окружения → файл в `secrets/`. Файл предпочтителен: он
  переживает и обновление, и пересборку базы.
- **Windows.** Пользователь запускает через WSL батником `START-NADZOR.bat`.
  Логин Windows в GitHub и логин внутри WSL — разные хранилища; батник
  подключает менеджер учётных данных Git for Windows к WSL.
- **Стоимость прогона.** Сверка комплекта в сотни листов — десятки и сотни
  обращений к модели, полтора часа реального времени. Это не зависание.
  Прогресс виден, прогон останавливается кнопкой.
- **Локальный `.venv` разошёлся с закреплёнными версиями** (`ruff` 0.16.3
  вместо 0.7.1). На результат линтера это не влияет — см. HANDOFF.md, §
  «Результаты проверок».
